# DECISIONS.md

## Вариант

Номер варианта: 2

Часть А: правило R7 — `cancel()` разрешён только из `DRAFT` и `SUBMITTED`; из `APPROVED` отмена теперь запрещена
(`IllegalStateException`: «Ошибка перехода: APPROVED → CANCELLED недопустим»). Из `REJECTED`, `CANCELLED` и `COMPLETED`
отмена по-прежнему запрещена.

Часть Б: `BusinessTripService.addIsCancellable(BusinessTrip) → boolean` — `true`, если статус `DRAFT` или `SUBMITTED`.
Для `null` выбрасывается `IllegalArgumentException("trip is null")`. Метод делегирует `BusinessTrip.isCancellable()`.

## Решение 1

Формулировка: правило отмены записано один раз — в методе `BusinessTrip.isCancellable()`; его использует `cancel()`
и `addIsCancellable`. Порог причины отклонения вынесен в константу `MIN_REASON_LENGTH`.

Альтернатива: повторить условие по статусам в `cancel()` и отдельно в сервисе.

Обоснование: два места с одним условием со временем разойдутся (ответ сервиса не совпадёт с поведением `cancel`).
Тест `B: результат addIsCancellable совпадает с поведением cancel()` это проверяет. Смена правила отмены — правка одного метода.

## Решение 2

Формулировка: статус меняется только доменными методами; в каждом сначала проверяется статус (`IllegalStateException`),
затем данные (`IllegalArgumentException`), и только после обеих проверок присваивается новое значение. Для проверки даты
`complete(LocalDate today)` принимает «сегодня» параметром, а `complete()` вызывает его с `LocalDate.now()`.

Альтернатива: публичный `setStatus` с проверками в сервисе; брать `LocalDate.now()` прямо внутри `complete`.

Обоснование: при ошибке объект не остаётся в промежуточном состоянии, а граничные даты (today = end и end − 1 день)
проверяются без зависимости от системных часов. Причина отклонения считается без пробелов по краям, чтобы строка из одних
пробелов не считалась причиной.

## Ответы на контрольные вопросы

### Вопрос 1

Наиболее вероятная ошибка входных данных — неверные даты командировки (начало позже окончания, пустое значение, неверный
формат), потому что даты вводит человек. Её перехватывает проверка в конструкторе `BusinessTrip`: `start == null || end == null`
и `start.isAfter(end)` приводят к `IllegalArgumentException("start must be <= end")`. Рядом стоит проверка `id.isBlank()` (R1).
Конструктор срабатывает до создания объекта, поэтому некорректная заявка не существует и не может попасть в сервис.
Разбор строк дат в `SelfCheck` превращает неверный формат в контролируемое сообщение или SKIP, а не в падение программы.

### Вопрос 2

Ключевое бизнес-правило — допустимость переходов между статусами (R3, R5, R7, R8), реализованная доменными методами
`submit`, `approve`, `reject`, `cancel` и `complete` класса `BusinessTrip`. Я разместил его в модели, потому что заявка
сама знает свой статус и поле `status` приватное: изменить его можно только этими методами, поэтому обойти правила
невозможно. Если бы переходы жили в `BusinessTripService`, любой код мог бы вызвать сеттер и нарушить их. Правило отмены
по варианту 2 собрано в одном методе `isCancellable()`, и `cancel()` использует его.

### Вопрос 3

Ромб «Переход допустим?» и блок A1 на Activity-диаграмме соответствуют первой проверке в каждом доменном методе, например
`if (status != TripStatus.SUBMITTED) throw transitionError(...)` в `approve()`. Ветка «нет» — это выброс
`IllegalStateException` без изменения статуса. Ветка «да» ведёт к блоку A2: в `reject` это проверка длины причины, в
`complete` — проверка `today.isBefore(end)`; ромб «Данные корректны?» соответствует этому `if`. Блок «Изменить состояние»
— строка `status = ...` в конце метода. Для `submit()` из `DRAFT` путь: допустим, данных нет, статус `SUBMITTED`.

### Вопрос 4

Минимального числа изменений требует смена минимальной длины причины отклонения, например с 10 на 20 символов. Меняется
одна константа `MIN_REASON_LENGTH` в `BusinessTrip`: условие в `reject` и текст сообщения используют её, поэтому
затронут один класс и одна строка. Логика переходов, сервис и диаграммы остаются прежними. Потребуется только обновить
ожидания `SelfCheck` на границе (10 и 20 символов) и строки CSV. Локальность достигается тем, что порог не размножен
по классам, а каждая проверка находится в одном методе.

## Фрагмент кода для анализа

```java
public void setStatus(TripStatus status) { this.status = status; }
```

Открытый setter нарушает инкапсуляцию: любой внешний код может записать любой статус и обойти проверки R3, R5, R7, R8 и R9.
Например, `trip.setStatus(TripStatus.COMPLETED)` переведёт заявку из `DRAFT` в `COMPLETED` без согласования и без проверки
даты окончания, а `REJECTED` можно сделать `APPROVED`. Исправление: удалить setter и менять статус только доменными
методами `submit`, `approve`, `reject`, `cancel`, `complete`, каждый из которых проверяет текущий статус и данные. Это
правило R10: `status` и `rejectionReason` приватны и не имеют setter, поэтому корректность переходов обеспечивает сам объект.
